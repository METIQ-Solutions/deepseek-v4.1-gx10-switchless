# Measured results — DeepSeek V4.1 Flash, 4× GB10, TP4, switchless ring

Our own measurements on the reference deployment, reported with the
configuration they were taken with and with their caveats. We publish what was
measured and retained, plus the tooling to reproduce the rest — not a table
padded with numbers nobody recorded.

## Hardware and configuration

| Item | Value |
| --- | --- |
| Nodes | 4 × ASUS Ascent GX10 / NVIDIA DGX Spark-class GB10, 128 GiB unified memory each |
| Interconnect | 2 × 200 GbE ConnectX per node, direct switchless ring, one physical cycle, two lanes per direction, no switch |
| Tensor parallelism | TP4, PP1, one head + three headless workers |
| Rendezvous | separate management network, head at `tcp://<head>:25001` |
| Transport | native NCCL `NET/IB` (RoCE v2), ring-only NCCL 2.30.7, `NCCL_ALGO=Ring`, Tree/PAT setup suppressed, 4 channels over 2 RoCE ports |
| Model | `deepseek-ai/DeepSeek-V4.1-Flash`, pinned revision |
| KV cache | FP8, block size 128, `BLNHC` layout, FlashInfer sparse-MLA backend |
| Engram | disk-backed from local NVMe |
| Speculative decoding | DSpark, `num_speculative_tokens=5` |
| Context | 1,048,576 configured; 32 sequences; 8,192 batched tokens |
| Scheduling | `priority` |
| Batch invariance | **off** (required on this fabric — see `docs/nccl-contract.md`) |
| Memory boundary | 104 G soft / 112 G hard / no swap, 16 GiB pre-start headroom |

## Results

Method: `benchmarks/scripts/benchmark.py`, streaming, temperature 0, prompts
calibrated against the server's own `/tokenize` so the reported prompt length is
the model's count.

| Point | Prompt tokens | TTFT | Effective prefill¹ | Decode² |
| --- | --- | --- | --- | --- |
| 128K | 130,752 | 68.454 s | ≈1,910 tok/s | ≈35.24 tok/s |
| near-1M | 1,048,283 | 949.635 s | ≈1,103.88 tok/s | — (prefill-only run) |

¹ `prompt_tokens / TTFT`. **Includes HTTP, queueing and transport time; this is
not pure GPU prefill speed**, and it must not be quoted as such.

² `(completion_tokens - 1) / (finish - first_token)`.

The near-1M point was a **genuine request**: the measured prompt length is
1,048,283 tokens (99.97% of the configured context), counted by the model's own
tokenizer, and the run required a retrieval code planted inside the measured
context to come back. It is not a configuration value or a startup log line.

### Independent cross-check

A different four-node GB10 deployment of the same model measured a needle at
993,435 prompt tokens with TTFT 982.4 s (≈1,011 tok/s) and ≈1,590 tok/s at a 48K
prompt. Our near-1M effective prefill sits in the same band. This is a
**third-party** figure used as a sanity band, not a result of this deployment.

## Negative result: large independent prefills serialize

At concurrency 4 with a 32K context, TTFT did not stay flat. The observed
staircase was:

```
15.96 s   32.22 s   47.60 s   62.65 s
```

The mechanism (derived from the scheduler source, and the reason the observed
numbers look like a staircase) is that `long_prefill_token_threshold` caps a
*single* request's chunk, while `max_num_scheduled_tokens` — falling back to
`max_num_batched_tokens` — bounds the *aggregate* scheduling step. With the
threshold disabled, the first waiting request consumes the whole per-step budget
and the others queue behind it. Raising the aggregate budget alone makes the
first request start sooner; it does not admit a second equal prefill.

The supported configuration deliberately keeps `--max-num-batched-tokens 8192`.
Admitting two ~8K prefills in one step would require
`--max-num-batched-tokens 16384` **together with**
`--long-prefill-token-threshold 8192`; that combination was identified from the
scheduler source but was **not** adopted, because the published configuration is
the one that was qualified end to end.

**Interpretation, not measurement:** this is why large independent prefills
appear to serialize. It is one scheduler's behaviour at one configuration, not a
statement that no faster configuration can exist.

## DSpark speculative decoding

DSpark was confirmed **operational** — speculative acceptance was observed rather
than assumed — and was treated as workload-dependent, never averaged across
categories.

We do **not** publish numeric per-position acceptance, tokens-per-step, or
low/high-acceptance figures: those runs were not retained. `k=5` is a
configuration default, not a measurement.

## Network utilisation

Retained evidence is **qualitative and structural**, not a utilisation
percentage:

* the four-node ring connected over **both** RoCE ports per node;
* subnet-aware routing selected the alternate RoCE device as designed;
* NCCL reported 4 collective channels and no Socket or Mesh tensor fallback;
* Tree and PAT transport setup was skipped by the ring-only build.

We did **not** retain per-edge ConnectX byte-counter deltas, per-interval RoCE
byte counts, or a measured statement of the form "the 200 GbE fabric was not the
bottleneck". `scripts/verify-cluster.sh` proves per-edge traffic moved during a
real prefill — the requirement the deployment was qualified against — but those
counter values were not archived as a published table. We therefore do not claim
them, and we do not confuse theoretical link capacity with a measured result.

## What was not measured

* 1K, 8K, 32K and 512K C1 points: defined in the suite presets, not retained.
* A C2/C4/C8 decode table: not retained.
* DSpark acceptance numbers: not retained.
* Per-rank memory headroom traces during the recorded runs: not retained.
* Any benchmark of a newer upstream vLLM candidate: it was not run.

Run `benchmarks/scripts/benchmark.py` and `scripts/verify-1m-context.py` to
produce any of the above for your own deployment, and compare against these
numbers only with the GPU clock-state check applied — see `docs/benchmarks.md`.
